# 说明浮窗与数值校准 · 第一轮

本轮目标：让玩家能理解并主动构筑，不追求把所有路线调成相同胜率。保留开局低回报、成型后高回报；不修改基础赔付表，不按玩家实时收入暗调目标。

## 可复现模型

- 在原型 worktree 执行 `npm run model:experience`。不读浏览器、不写存档、不跑旧的大规模 Monte Carlo。
- 基础机器精确枚举 12³ = 1,728 个停点组合，保留同一轮三格相邻关系。
- 每个合成构筑使用相同 64 个种子：`(820127 + Math.imul(i, 0x9e3779b9)) >>> 0`。
- 每样本通过真实命令处理 3 次付费转及其产生的免费转，最多观察 12 次实际转动。
- B 表示当前固定下注。初始余额设 100B，排除早期破产干扰。餐费／献祭计入净收益。
- 所有结果直接收下，无重转、锁轮或踹击策略。小教堂在开始时献祭并祈祷幸运7；厨房样本在首转前买餐。
- 改前 13 组，改后另加“小教堂满配”作为当前可达上界探针。构筑是人工配置，不表示玩家能在第几班获得。
- 原始结果：`artifacts/experience-before.json` 和 `artifacts/experience-after.json`。改前规则指纹 rules-28b17281d12b0627；改后规则指纹 rules-76b3ccda2416e7f9，已核对本地 5173 服务。

## 1. 基础机器不是收益引擎

每轮初始概率相同：樱桃 4/12、柠檬 3/12、铃铛 2/12、幸运7 1/12、百搭 1/12、空白 1/12。

某普通符号 s 在单线中奖的概率：

`q(s) = ∏(p(s)+p(百搭)) − ∏p(百搭)`

全百搭单独结算。5 条线的期望可相加，但命中事件彼此相关，不能当成 5 次独立抽奖。

`E[基础赔付]/B = 5 × (0.6×124 + 0.9×63 + 1.5×26 + 3.5×7 + 5.5) / 1728 = 57.8993%`

精确任意中奖率 48.50%，赔付高于一笔下注的概率 16.55%。这不含躁动、服务、部件或干预，不能称为完整机器 RTP。基础表本轮不改，玩家需要构筑才能翻转期望。

## 2. 控制成型樱桃的增长，保留早期手感

纯樱桃盘面每转 5 条线，三转 15 条。L2 果酱＋L2 压榨机，在没有食物图案打断的理想情形：

- 原规则：基础 9B ＋压榨 18B ＋果酱 (0+1+…+14)B = 132B；全程 +50% 餐加成为 198B。
- 新规则：果酱每条只计此前最多 6 层，果酱合计 69B；总额 96B，餐后 144B。
- 计数日志仍保存真实累计线数；只有有效奖金层数封顶，换班照常归零。

同种子模型验证：

| 三转构筑 | 改前平均赔付 | 改后平均赔付 | 改前 / 改后中位数 |
| --- | ---: | ---: | ---: |
| 成长中樱桃 L1＋厨房 | 8.4531B | 8.4414B | 7.95B / 7.95B |
| 成长中樱桃 L2＋厨房 | 13.2188B | 13.1953B | 11.55B / 11.55B |
| 纯樱桃双 L2＋厨房 | 186.7938B | 140.7234B | 198B / 144B |
| 纯沙拉双 L2＋厨房 | 110.0977B | 110.0977B | 112.5B / 112.5B |

餐费不影响总赔付，但影响净收益。购买的食物图案会暂时稀释纯图案盘面，所以样本均值小于理想上界。此改动主要收紧成型上界，未削弱成长中构筑的典型一班。

## 3. 食物定价和献祭封顶

标准下注是自由模式的正常档下注，或客房固定下注；与玩家当前保守／激进档无关。

- 餐费：固定 ¥10 → 标准下注 ×0.75。初始 ¥7.5；三间客房为 ¥18.75 / ¥37.5 / ¥75。
- 这样避免高额下注时餐费几乎为零，也不允许切低档买餐再切高档套利。
- 无部件的基础样本：餐前平均净收益 −1.1891B；新餐价下 −1.1090B。这个微小差异不足以证明裸机必买餐，64 种子不是显著性检验。成型引擎从餐中获得的绝对收益更明显。
- 殉道者献祭：`min(ceil(余额×10%), 标准下注×2)`。财富积累不再把每班启动成本推至无限。
- 同一成长中小教堂样本，在 100B 初始余额下，献祭费从 10B 降为 2B，平均净收益增加 8B；赔付分布完全不变。这是定价改善，不是命中率改善。
- 什一税箱仍是一次性升级 ¥10，未改成服务餐价；小费精修仍为 3 枚，未改掉落池。

## 4. 故障线先解决“核心自己先坏掉”

废料磁铁与保修欺诈现在免疫裂纹失效。裂纹仍按右至左禁用其他部件；空槽不挡伤，消除裂纹不追溯恢复已失效部件。

仅装磁铁的固定损伤转轮：平均部件收入从 0 → 0.625B / 三转，平均总赔付从 0.9781B → 1.7063B。它现在可以启动，但仍不是稳定赚钱的完整构筑。

重要限制：五部件故障样本改后 3/64 超过 12 转观察上限。它们在窗口内已付 16.35B、16.10B、15.90B，尚未完成一段。JSON 明列截断样本；其余 61 组均值不是无偏整段结果，不能据此宣称故障线已经平衡。后续需专门评估长免费转的节奏、退出方式和成长能力，本轮不偷偷加入免费转硬上限。

## 5. 客房是公开的构筑考题

| 客房 | 下注不变 | 原目标 | 新目标 | 新目标 / B |
| --- | ---: | ---: | ---: | ---: |
| 花园房 | ¥25 | ¥450 | ¥450 | 18 |
| 景观房 | ¥50 | ¥1,500 | ¥2,000 | 40 |
| 顶层套房 | ¥100 | ¥5,000 | ¥11,000 | 110 |

专注上限仍为 3 / 2 / 1。开局五班、三次付费转结构、所有已获得奖金均不改变。

新顶层阈值下，人工满配样本超过 110B 的占比：樱桃 64/64、沙拉 54/64、小教堂 45/64。顶层可以奖励真正完成的引擎，并不要求完美构筑仍然经常失败。

这只是把普通固定下注样本的归一化赔付与房间目标比较，不是实际入住模拟，更不是玩家通关率；没有考虑拿到部件的难度、重转策略、余额、跨班食物与转轮演化。小教堂满配也未在改前跑过，不能用于声称前后改善。

纯柠檬三转基础上界仅 13.5B，加餐典型 20.25B，适合花园房和自由加班，单靠它原本就不足以过全部房间。未来若要让每个水果分支都能独立通顶，需要柠檬后期引擎，而不是只提高房价。

## UI 交付与边界

- 手机点开的说明浮窗：消耗、效果、限制、当前状态。键盘可关闭、焦点返回；背景不可操作，自动停轮／确认／结算推进暂停。
- 专注、小费、躁动、恶兆、永久裂纹总数、食物、下注、祈祷、餐费、献祭、重转、锁轮、踹击、维修、部件和升级都有就地说明。
- “玩法与术语”可在游戏内打开，前台“玩法与设置”共享同一份介绍；路线、词典、赔付例子与统计边界按章节折叠。
- 现有会计模拟仍未纳入完整实时状态及三转重置；本轮增加醒目标注，没有冒充已修正的精确预测器。
- 规则变化会生成新指纹。旧局保留查看、导出，不强行套新规则；体验新数值要开始新局。
- 数学结果证明部分规则差异，不证明更好玩。后续以真实游玩日志观察选择是否更容易理解、食物是否有决策感、故障连锁是否拖沓。
